# 社媒增长通用流程

> **本文件统一覆盖两类社媒增长任务**，通用部分共享，任务专属部分分别说明：
>
> 1. **任务 A · explore + reachout（主动触达）**：浏览新帖 → 探索评论区 → 回复 → 入库。角色定位是 **explore + comment agent**。
> 2. **任务 B · inbox reply（通知回复）**：打开「通知」→ 看留言 → 判断 → 回复 → 入库。角色定位是 **inbox reply agent**。
>
> 本文件是唯一需要保留的 markdown。沙箱销毁后所有文件清空，未来使用者不一定是原作者，因此下文的具体值均已抽象为变量。每次执行前先向主人确认变量。
>
> **文档归属规则**：跨平台、跨语言环境都成立的规则只写在本通用文档；仅针对某平台界面、交互或已知坑的优化，才写在对应平台文档。引用其他文档或目录时不得依赖固定的绝对/相对路径，应按当前工作区实际目录结构定位。

## 0. 变量表（任务开始时向主人索取具体值）

> 注：「主人」= 下达指令的人（账户持有者），不是变量。

### 通用变量

| 变量 | 含义 |
|---|---|
| `{社交媒体}` | 目标平台名 |
| `{产品}` / `{PRODUCT_NAME}` | 产品本地化名字 |

| 变量 | 含义 |
|---|---|
| `{COMMENT_KPI}` | 评论数量目标（如 100） |

| 变量 | 含义 | 说明 |
|---|---|---|

## 1. 通用核心指示（两类任务都必须遵守）

> **全局法则（i18n）**：产品名等对外文案按目标平台本地化——中文平台用中文名、不用英文名。商定变量时即已考虑 i18n。

**目标**（在社媒平台引流产品；**不在平台直接提 URL/域名**，防触发平台限制）：

1. **可能有需求** → 通过回复**引出对方的需求**（摸底、反问）。
2. **有明显符合我方 features** → 直接问对方**是否需要该功能**。
3. **对方明确回复/表明自己要** → 标记 candidate 汇报主人，**主人批准后**再说「可以发邀请码」（邀请码由主人私信发，agent 只承诺不披露）。
4. **纯情感宣泄/抑郁** → 同样**关心和共情**对方，博得好感。

**方法：广搜索（或广响应），精准引流。**

1. 浏览尽可能多的人/评论：任务 A 用主页推送 / 关键字搜索，任务 B 用通知 inbox。
2. 识别其中符合产品特性的需求（显式或隐式）→ 一轮或多轮回复确认兴趣（**仍不具体告知域名**）→ 提产品特性 → 私信邀约。

**回复整体风格**：根据对方回复的上下文，**纯好奇对方的现状，让对方自己说出痛点**。

- 价格痛点例：「主要是贵…」→ 建议回「确实😮‍💨 你目前有在用什么吗还是一直在观望」
- 明确在找方案例：「这创意不错，这东西好像还真没人做」→ 「真的，这个需求感觉挺多人有的🤔 你现在是用什么凑合的」
- 小白门槛痛点例：「她不会运行Python脚本，前教后忘记」→ 「哈哈前教后忘太真实了😂 后来呢有解决没」

**回复准确性**：回复中若包含知识类回答，**必须查证事实**，不能依赖自己的判断/过期知识。

**走心 + 千人千面**：禁止 mode collapse（千篇一律的话术）。针对对方留言动机定制独一无二的评论，真诚回答疑惑/技术问题或引发深度讨论，不留统计性规律。

### 1.1 通用回复纪律（逐条执行）

1. **事实性问题**：先通过搜索 / research / 仔细求证 / 查看帖子上下文，得到答案再回复。
2. **没发现答案、或对方在问你不知道如何回答的问题（比如关于我、关于我的评价）→ 不要回复**，并总结给主人。
3. **情感向帖子**：多真心体谅用户内心需求，回复有共鸣和心理安慰的句子。**不用有任何引导**，只与用户做简单和直接的交流。
4. **文风**：所有回复尽力直接不要绕弯，可以幽默，但不能有太多 AI 味，不要超必要的冗长。
5. **反问引导**：如果觉得反问用户可以引出更多信息，请反问——最终目的是希望引出用户对我们产品感兴趣的点。
6. **识别兴趣**：如果用户明显对我们的产品（或产品特性，参见 `{产品特性页}` landing page）感兴趣，记录并回复。
7. **潜在兴趣用户邀请与互动策略（先 candidate，主人批准后才邀请）**：识别到用户对 `{产品}`（或某特性，参见 `{产品特性页}`）有潜在兴趣时，**当场不发邀请**——先围绕痛点或技术共鸣进行探讨/反问（**不提域名**，防止被平台封禁），把用户标记为 candidate（`invite_status='candidate'`），保持多轮互动，**完整记录用户和帖子上下文**，汇总给主人。常规技术探讨与共鸣回复可自主决策发送并入库，遇不确定或重大策略时向主人请示。**只有主人明确批准后**，才对相应用户说「是否要个邀请码 / 我有邀请名额，私信我帮你安排」之类的邀请话术（**永远不要说出或索要邀请码本身**），并把状态更新为 `invited`。
8. **合理性与真实感原则（不突兀、不生硬转移）**：
   - 严禁对未上线/推测性模型进行不合理的深度体验提问。
   - **不要回复跟上下文无关的生硬话题转移**。如果实在和产品没有太大关系，就真诚共鸣回复一下（如针对开发者痛点、模型使用体验、行业现状等），保持真实开发者交流氛围。
9. **入库要求与无脚本依赖（纯 Markdown 自包含）**：所有你的回复都必须数据库入库。**必须包含对方的文字和你的文字**；识别到潜在兴趣用户时标记 `invite_status='candidate'`。入库直接使用 Python/psycopg2 写入数据库（见 §6 自包含代码模板），**严禁在本地生成多份独立的 `record_xxx.py` 临时文件，也不要假设本地预存了任何 `.py` 工具脚本**，仅凭本 markdown 即可自包含执行完整流程。
10. **完成通知**：完成所有回复以后，在这里通知主人。如果你没发现任何可回复的用户，也完全没关系，在这里告诉主人就行。

### 1.2 产品名与推销节奏

- 中文平台用本地化名 `{PRODUCT_NAME}`（不用英文名）。诚实说明是小范围内测、可能存在不稳定性；提供免费试用，**时长等细节以 `{产品特性页}` 为准**。邀请码由主人生成，我们**不主动提及邀请码内容**。
- **一般情况：第一轮回复不提产品，先摸痛点**（上来就提产品名容易引起防御心理）。
- **例外（perfect product-demand fit）**：用户痛点跟产品完美匹配时可直接提产品名，不绕弯；但**发邀请话术仍须先经主人批准**（见 §1.1 第 7 条）。
  - 典型场景：用户求「稳的🪜」类需求（命中产品核心能力）→ 正确回法：先描述产品能力并提产品名（如「这种需求可以免费试用一下{PRODUCT_NAME}，我们正在小范围内测的产品」），标记 candidate 汇报主人；**主人批准后**再补「我有邀请名额，私信我帮你安排」。（错误回法：把自己放在需求方位置，后面没法转推销）
  - **这类需求为何命中核心能力**：产品服务器部署在国外 + 自带浏览器自建能力，天然可帮国内用户实现稳定的「科学上网」。这是产品的**低调卖点**，只在用户明确命中该需求时顺势提及，不主动宣传、不写成通用文案。
  - **邀请码本身永远由主人私信发送**，agent 永远不接触、不披露邀请码；agent 在平台上只在**主人批准后**承诺「可以邀请/看私信」，并把用户记录入库（`invite_status='candidate'` → 批准后 `'invited'`），由主人后续逐个私信发码。
  - 判断标准：用户需求是不是产品能**直接、立刻**解决的？是→直接提；不是→先摸底。

## 2. 通用执行环境与登录态确认

- agent-browser 用 `--session <name>` 做 **tab 隔离**：每个 agent 在自己的 session 里开自己的 tab，别和其他 agent 的 tab 冲突。
- 登录态判断：直接看浏览器里平台的页面显示——是否有自己账号的头像 / profile / 已登录状态。**不要用 `document.cookie`（httpOnly 读不到）或 localStorage 判断登录态**。
- **会话复用**：需要开会话就开；不需要新会话就找到自己之前的 session，在里面继续工作，别重复开。
- **每个 session 的 tab 数控制在 3 个以内（防 OOM）。**
- 使用浏览器而非命令行操作（防平台封号）。
- session 名在会话开始时由 agent 自己决定（可取随机值），整个会话固定沿用：`agent-browser --session <会话开始时自定的名> ...`

## 3. 任务 A · explore + reachout（主动触达）

### 3.1 任务 A 专属纪律

1. **匹配优先（最重要）**：回复前必须确认帖子/回复里存在与 `{产品}` 定位或功能相匹配的内容（显式或隐式需求）。情感向内容也可能匹配，但**少回**；**明显不匹配的一律跳过不回**。
2. **路上随机点赞**你觉得有意思和喜欢的 posts：**每隔 3 个你的评论至少要有 1 次点赞行为**（长时间只评论不点赞不是正常账号轨迹）。
3. **只去寻找我们自己没有回复过的帖子或者回复**（用数据库去重，见 §6）。
4. **每个帖子只选取少量**潜在用户回复（**每帖 3-4 条封顶，宁缺毋滥**）；识别并过滤明显的推销评论（销售、拉群、引流号，不回复）。
5. **优先回复近期**评论的用户（老的回复可能用户已不需要/已找到方案）。
6. **完成评论 KPI（`{COMMENT_KPI}`）以后，在这里通知主人。**

### 3.2 获得帖子列表（搜索只是其中一种方式）

> 获得新帖的方式不限于搜索：**时间线 / 首页推送 / 推荐流 / 关键字搜索都可以，随机逛就行**。

1. 打开平台首页，从时间线/推送/推荐流直接逛，或用搜索框搜 `{KEYWORDS}` 里的关键词。
2. 滚动加载更多帖子。
3. 收集帖子列表（标题 + 帖子链接）。

### 3.3 进入帖子并读取内容

1. 点开目标帖子。
2. **进入新帖后先刷新一次**，确保读到的是当前帖子的内容（避免残留上一个帖子的旧数据）。
3. 读取帖子正文与评论区：帖子标题、正文、帖主昵称，以及评论列表（每条评论的评论者昵称/ID、原文、子回复）。

### 3.4 点赞（账号轨迹需要）

给觉得有意思/喜欢的帖子点赞，维持正常账号轨迹（见 3.1 第 1 条）。

### 3.5 定位并回复目标

> **默认回留言**（留言更可能是真实观众，而非推销号）；**帖子本身（楼主帖子）也可以是我们该回复的对象**——当帖子正文本身值得回应、或评论区没有合适留言时，直接回帖本身。

1. 定位目标（留言，或帖子本身）：按昵称 + 必要时按原文双重匹配，防同名用户匹配错。
2. 点开回复编辑器，输入回复内容，点发送。
3. 验证：刷新后出现我方账号昵称的回复，或输入框已清空。

### 3.6 入库（防重复 + 留痕）

- 每条回复发出后**立即入库**（upsert 保证幂等，见 §6）。
- 唯一键：`UNIQUE (target_user_name, target_text)` —— 防止重复回复同一条留言（或帖子）。

### 3.7 帖子间切换

进帖后列表被覆盖 → 循环：**回首页 → 重新搜索/重新逛 → 点下一个帖子**（不尝试在帖子页找列表链接）。

### 3.8 完成后汇报

完成 `{COMMENT_KPI}` 后向主人汇报：**回复总数**、KPI 达成情况、**candidate 清单**（`invite_status='candidate'`，待主人批准后再发邀请话术）。无用户可回也如实告知。

## 4. 任务 B · inbox reply（通知回复）

### 4.1 ⚠️ 重点中的重点（每次执行都必须做到）

1. **只在自己的「通知」系统里干活**：只看**收到的评论**和 **@（AT）**。不搜索、不逛推荐流、不主动去别人帖子下找评论——那是任务 A。
2. **收到一条 → 立刻点进去 → 先确认再回复**：点开通知 inbox item，进入**原始帖子和评论地点的上下文**，彻底展开目标 thread，并按时间顺序确认**最末一条是谁发的**，再决定是否回复。
3. **严禁重复回复；以 thread 最末消息为准**：最末一条是我方 → 不回复；即使对方此前连续回复 N 条，也视为我方已在其后统一回应。最末一条是对方 → 回复一次；即使 thread 更早处有我方历史回复、且对方在其后连续发了 N 条，也应针对这批消息统一回复一次。若发现我方存在重复回复，删除多余回复，只保留时间上**最后一条我方回复**；保留的回复必须在对方最后一条消息之后。
4. **看到一条待回复的，就回一条**。不要先收集完整名单再统一回复——逐条处理，边看边回。

### 4.2 任务 B 专属回复策略（补充）

- **死话也回一句**：如果你觉得用户不需要回复，比如他已经明显把话说死了，或者表明对我们产品没有兴趣，你也完全可以忽略。但请回复一个无关痛痒的简短文字，比如「嗯嗯」之类的。**用于 mark 我们的通知 inbox 哪些用户已经被回复。**
- **跳过规则**：**被对方删除、或上下文已被删除的留言，一律跳过（不入库、不回复）。**
- **操作方式红线**：除了数据库入库之外，**抓取、查看上下文、回复一律不允许写脚本**，必须手动通过 `agent-browser` 操作。

### 4.3 抓取通知 inbox（手动 agent-browser，禁脚本）

1. 用 `agent-browser` 打开平台首页，从账户菜单进入「通知」（如头像 → 消息/通知）。若浏览器未登录该平台，请主人先登录。
2. **逐条处理，看到一条回一条**：进入通知列表后，**点开最新的 inbox item 进入原始帖子/评论上下文**，而不是先滚动收集完整名单。
3. 每条留言进入上下文后确认：对方昵称、对方原文、帖子是否还在，并**完整展开 thread 后确认最末一条是谁发的**（关键！）。
4. **跳过**：留言被删、上下文帖子被删/不可见、无法定位到对应帖子评论 → 一律不回复。
5. **重复回复处理**：若最末一条为我方，不再回复；若最末一条为对方，即使我方曾在 thread 较早位置回复过，也回复一次。只有在我方存在多条重复回复时，才删除多余项并只保留最后一条我方回复。
6. 处理完一条再回到通知列表拿下一条，直到当前可见的未回复留言都处理完。

### 4.4 手动回复（逐条处理，模拟真人节奏）

1. **看到一条待回复的就回一条**：处理完一条再拿下一条，不等收集完整。
2. **回复前必须已在上下文里完整展开目标 thread，并确认最末一条是对方发出的**（见 §4.1 第 2–3 点）。
3. 每条：`agent-browser` 定位留言 → 点回复 → 键入 → 发送 → **肉眼确认发出成功**。
4. 若发现我方存在多条重复回复：删除多余的，只保留时间上最后一条我方回复；如果最末一条是对方，则按本轮待回复处理，不因历史回复跳过。
5. 一条一条来，不并发、不批量注入；批间自然停顿，像真人刷手机。

### 4.5 完成后汇报

处理完可见留言后向主人汇报：**未回复名单**（被跳过/无法回复的留言及原因）+ **candidate 名单**（`invite_status='candidate'`，待主人批准后再发邀请话术、逐个私信）。无用户可回也如实告知。

## 5. 回复分类与判断（通用）

| `reply_type` | 含义 | 何时用 | 适用任务 |
|---|---|---|---|
| `factual` | 事实问答 | 回答知识/技术问题，**必须先查证** | 通用 |
| `emotional` | 情感共鸣 | 情感向帖子，真心体谅，不引导 | 通用 |
| `question` | 反问摸底 | 觉得反问能引出更多信息（默认首选） | 通用 |
| `invite` | 直接邀请 | perfect product-demand fit，提产品名+发邀请话术；**必须先经主人批准**（先 candidate 后 invited），邀请码由主人发 | 通用 |
| `skipped` | 过滤 | 推销评论（销售/拉群/引流号）、删除的评论、失效链接、无法回答的问题 | 通用 |
| `deadend` | 死话 | 「哈哈」「不错」「知道了」等无意义，简短回应标记已读 | 任务 B |
| `normal` | 普通 | 常规简短回应 | 任务 B |

## 6. 数据库设计（通用模板）

> **表名规则（写死，绝无歧义）**：`{DB_TABLE}` = `{sns_FOO_task_BAR}`，其中 FOO = 平台名、BAR = 任务名（统一使用下划线避免 SQL 连字符转义问题）。任务 A → BAR=`reachout`，任务 B → BAR=`reply`（例：平台 `xhs` 的任务 A 表 = `sns_xhs_task_reachout`，任务 B 表 = `sns_xhs_task_reply`）。不存在就 `CREATE TABLE IF NOT EXISTS` 创建，绝不用临时表名。字段是两份文档的并集，按需取用。

> **⚠️ 可逆定位（最重要，违反则数据作废）**：每条 item 入库后，**必须保证 retrieve 出来能重新定位回原始帖子和回复**——要么能构造链接直接打开，要么能凭字段在平台里**搜索**回评论地点和上下文。**特别注意：部分平台（如小红书）的 URL 有时效性、会失效**，所以绝不能只依赖 `post_url`。建表时必须定义足够多的定位字段（帖子标题、帖主 id、回复对象 id、对方原文等），并**写死为 required（NOT NULL）**，靠它们支撑搜索定位。

> **parent 与 target 的关系**：`parent_*` 固定是**楼主帖子**；`target_*` 是**我们回复的对象**（默认回留言，也可回帖本身，见 §3.5）。回帖本身时 `target_*` 与 `parent_*` 相同（如 `target_id = parent_post_id`），两者**可以是一样的**。

```sql
CREATE TABLE IF NOT EXISTS {DB_TABLE} (
  id                  serial PRIMARY KEY,

  -- parent · 楼主帖子（可逆定位锚点，required）
  parent_post_id      text NOT NULL,   -- 帖子 ID
  parent_title        text NOT NULL,   -- 帖子标题（搜索定位用）
  parent_user_name    text NOT NULL,   -- 帖主昵称（搜索定位用）
  parent_user_id      text NOT NULL,   -- 帖主 ID（搜索定位用）
  parent_url          text,            -- 帖子完整链接（⚠️ 有时效、会失效，不可作唯一定位）

  -- target · 我们回复的对象（可逆定位锚点，required）
  -- ⚠️ 默认回留言；也可能是帖子本身，此时 target_* 与 parent_* 相同
  target_id           text NOT NULL,   -- 回复对象 ID：留言 ID，或回帖本身时 = parent_post_id
  target_text         text NOT NULL,   -- 对方原话：留言原文，或回帖本身时 = 帖子正文
  target_user_name    text NOT NULL,   -- 对方昵称：留言作者，或回帖本身时 = 帖主
  target_user_id      text NOT NULL,   -- 对方 ID：留言作者，或回帖本身时 = 帖主

  -- 我方回复
  our_context         text,            -- 我们之前的评论/提问（上下文；首轮可为空）
  reply_text          text,            -- 我们发出的回复原文

  -- 通用元数据
  tags                text[] DEFAULT '{}',
  reply_type          text NOT NULL DEFAULT '',          -- factual / emotional / question / invite / skipped / deadend / normal
  invite_status       text NOT NULL DEFAULT 'none',     -- none / candidate（待主人批准）/ invited（已批准并发邀请话术）
  status              text NOT NULL DEFAULT 'new',       -- new / replied / skipped / failed / answered_no
  replied_at          timestamptz,
  created_at          timestamptz NOT NULL DEFAULT now(),

  UNIQUE (target_user_name, target_text)                -- 防重复入库
);
```

常用查询：
```sql
-- 待回复的潜在用户
SELECT * FROM {DB_TABLE} WHERE status='new' AND reply_type IN ('question','emotional','factual') ORDER BY created_at;
-- 潜在邀请对象（主人审批用）
SELECT target_user_name, target_user_id, parent_title, parent_url, target_text, reply_text
FROM {DB_TABLE} WHERE invite_status='candidate' ORDER BY created_at;
-- 已发出邀请话术的（主人逐个私信发码用）
SELECT target_user_name, target_user_id, parent_title, parent_url, target_text, reply_text
FROM {DB_TABLE} WHERE invite_status='invited' ORDER BY replied_at;
-- 全部已回复
SELECT * FROM {DB_TABLE} WHERE status='replied' ORDER BY replied_at;
```

⚠️ **连接坑**：密码直接写进 shell 命令会被系统打码（`***`），导致认证失败。
**解法**：使用 Python `psycopg2` 执行数据库操作（可通过 `execute_code` 或内联 Python 运行）。
