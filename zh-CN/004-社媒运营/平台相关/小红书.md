# 小红书 Inbox Reply 实战经验

## 核心原则

1. **用户说一步做一步**，不跳步，不自作聪明。
2. **回复前必须确认有没有回复过，绝对不准自己回复自己！** 永远不要靠记忆猜。
3. **严禁千篇一律与模式崩溃（Mode Collapse 零容忍）**：**绝对严禁使用固定话术模板，绝对不能把一句话或相似句式回复给多个人！** 每条回复必须针对对方原帖/评论的具体语境、用词、卡点量身定制。
4. **单帖回复限制与强差异化**：**同一帖子下默认最多回复 2 条**，回复 1~2 个后原则上立即换新帖。若该帖/thread 下确有极高价值潜客非要回复超过 2 个，**必须绝对严格基于该用户上下文独立回复，且绝对不能与该帖子/thread 下所有其他回复有任何相似性**。
5. **潜在用户保持多轮互动**：发现痛点用户标记 `candidate`，常规探讨/共鸣自主把控，重大策略请示主人。
6. **入库自包含与无脚本假设**：所有入库操作直接使用 Python `psycopg2` 执行（自包含代码模板详见通用规范），**严禁假设本地存在任何 `db_helper.py` 或预存 `.py` 脚本，也严禁本地生成多份一次性的临时脚本**，所有执行依据和代码片段均以 Markdown 自包含为准。

## ⚠️ 铁律（每次执行必读）

1. **宁肯错过，不能 spam 对方！** 不确定有没有回复过 → 不回。宁可漏掉一条，也不能重复回复骚扰用户。
2. **🚨 严禁自回复（最高安全红线，三令五申）**：绝对严禁回复我方账号（包括当前登录的主账号、我方所有关联子账号矩阵/变量名 `{我方账号昵称}` 等）。回复前必须严格核验目标用户昵称，若目标为我方账号一律直接跳过！
3. **每条 scan 过的评论都必须入库 `sns_xhs_task_reply`**，无论是否回复（已回/死话/跳过均入库）。下次不用点进帖子就能知道已处理过。
3. **通知页浮层与 Tab 策略**：
   - 小红书通知点击后通常以**模态浮层（Modal / `.note-detail-mask`）**覆盖在当前页面。
   - 处理完毕后，**必须点击右上角关闭按钮（`.close-icon` / ref `e1`）或按 `Escape` 键关闭浮层**，再处理下一条通知。
   - **踩坑预警**：若浮层未关闭就直接点击通知列表其他项，会被遮罩层拦截报错 `is covered by <div.note-detail-mask>`！
4. **回复前必须点进帖子 + 展开折叠回复**，确认没有自己的历史回复后才能回复。绝对不能用通知页的内联回复。
5. **展开回复必须彻底！** 一个 thread 下可能有多层「展开更多回复」，必须**反复点击直到全部彻底展开（直到展开按钮消失）**，确认整个 thread 下没有自己的回复才能回复。只展开一次是不够的！
   - **只展开目标 thread！** 不要展开评论区里其他无关的 thread，只点当前这条通知对应的「展开更多」。  
6. **判断是否已回复的规则：** 针对同一个用户，如果 thread 里最近一条回复是我们发的，就算已回复！即使对方有多条回复，我们也只需要回复一次。不要因为对方又回了一条就重复回复。
7. **检查流程（严格执行）：** 点进帖子 → 找到目标 thread → 反复点「展开更多回复」直到展开按钮消失 → 检查所有回复文本 → 确认没有我方账号（当前登录账号/变量 `{我方账号昵称}`）的回复 → 才能回复。绝对不能草草扫一眼就下结论！

## 为什么不能用内联回复

- 通知页的「回复」按钮展开内联回复框，**看不到该评论线程下有没有自己的历史回复**。
- 正确做法：点击通知文字进入帖子浮层/页面 → 找到评论线程 → 彻底展开折叠回复 → 确认没有自己的回复 → 再回复。

## 回复后必须入库与无外部脚本依赖

- 每回复完一条，**立刻**写入数据库表 `sns_xhs_task_reply`。
- **无外部脚本假设原则**：不要假设本地存在 `db_helper.py` 等辅助脚本。直接在 Python 环境（如 `execute_code` 或临时内联执行）中引用数据库连接参数完成 insert/upsert，禁止为每条记录生成独立的 `record_item*.py` 文件。
- 查询状态使用内联 SQL 执行：`SELECT * FROM sns_xhs_task_reply WHERE invite_status='candidate';`。

## 数据库配置与表名

- 正确表名：`sns_xhs_task_reply`（下划线），不是 `sns-xhs-task-reply`（连字符）。
- 数据库连接：PostgreSQL `host="db", port=5432, dbname="db_xhs", user="user_c0c088f8", password="CUEZ_Q_7_z6avgIucyy5UA"`。
- 入库用 psycopg2 连接（psql 命令行密码会被系统遮掩导致认证失败）。

## 通知页操作流程

1. 打开小红书 → 点「通知」→ 确认在「评论和@」tab。
2. 逐条处理，每条流程：
   - 记录通知内容（对方用户名、留言、我的原评论、时间）
   - **点击对方回复文字或我的原评论文字**，直接跳到评论浮层/上下文（不要点帖子缩略图，不要点用户名）
   - 若进入浮层，等待渲染完毕，若评论区较长，定位至 `.note-scroller` 滚动查找
   - 反复点击目标 thread 下的「展开更多回复」，直至按钮消失
   - 确认整个 thread 中没有我方账号（当前登录账号/变量 `{我方账号昵称}`）的回复
   - 如果没有 → 结合上下文决策回复（**不要回复跟上下文无关的生硬话题转移；若和产品没太大关系，就真诚共鸣回复**）→ 执行入库
   - 如果已有回复或属 deadend → 记录状态入库
   - **关闭浮层**（点击 `.close-icon` 或按 `Escape`），回到通知列表，处理下一条。

## 回复分类与策略

- **潜在用户（Pain Points）**：卡在海外手机号、环境搭建、多卡功耗、移动端review等 → 引导至云端独立沙箱工作台/环境，标记 `invite_status='candidate'`，保持多轮沟通。
- **死话 / 无实质互动**（"😅"、纯表情、单字"私"、"对！"）：标记 `status='ignored_deadend'` 入库，无需产生低质回复。
- **事实/技术问答**：必须先查证事实再回复（严禁凭推测胡说，如模型未发布却问体验）。
- **已删除评论**：跳过，标记 skipped。

## 已知坑与实战教训

- **遮罩层拦截**：浮层未关闭时点击通知项会报错，必须每条处理完后关闭浮层（`Escape` 或 `click .close-icon`）。
- **长评论滚动**：评论区有独立滚动条 `.note-scroller`，长帖需滚动到底部或用 DOM 选择器定位。
- **展开检查必须彻底**：曾发生因未完全展开多层回复而误判漏看历史回复、导致重复回复的问题。教训：必须点到展开按钮彻底消失！
- **回复前必须确认事实**：曾发生用户问"等恢复吗"，回复"在等"但 GitHub 实际已恢复的尴尬情况。教训：涉及状态/事实问题必须先 verify。
- **严禁自回复与账号校验（最高安全红线）**：DOM 选择器或上下文匹配若不严密，极易误将我方账号（当前登录账号、我方子账号矩阵/变量 `{我方账号昵称}`）识别为目标对象。**绝对不准自己回自己！** 在点击回复和入库前，必须严格校验目标用户昵称，若目标为我方账号一律立即跳过。
- **单帖回复上限与同帖强差异化硬约束**：**同一帖子下默认最多允许回复 2 条**，回复 1~2 个后原则上立即切走换新帖，坚决不在单帖堆叠回复。**特殊情况**：若 thread 下有多个明显高价值潜客非要回复 >2 条，**必须必须严格根据该用户的独特上下文展开，绝对不能与同一个帖子/thread 下所有其他回复有任何相似性（切入点、句式、用词完全隔离）**。
- **严禁千篇一律与模式崩溃（Mode Collapse 零容忍）**：绝对严禁模板化套话，严禁一句话回多个人，每条必须针对对方具体上下文与用词量身定制。
- **切忌 Double Reply 与防 Spam 结贴机制**：若 thread 中最近一条回复已是我方发送，或对方仅为客套表情/短句自然结贴，坚决不跟进二次回复，宁肯错过也绝不给用户造成骚扰感。
- **命令行密码脱敏导致连接失败**：沙箱环境下通过 Shell 命令行（如 `PGPASSWORD=... psql`）传递密码会被底层安全机制脱敏（Sanitize），导致密码校验失败。所有数据库入库与查询推荐统一使用 Python `psycopg2`（通过 `execute_code`）完成。
- **搜索强制按时间排序（最新）与交替法则**：
  1. 若使用顶部搜索栏搜关键词，**搜索结果出来后必须点击筛选条件切换为「最新」**。非大爆款尽量不要看几个月前的老帖，防止潜在用户需求已过时。
  2. 搜索行为与刷主页推荐流（时间线）必须**交替进行**（跟点赞策略一样），严禁像机器人一样死盯着搜索结果狂刷。
