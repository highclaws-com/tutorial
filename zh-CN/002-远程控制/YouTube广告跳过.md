# 跳过 YouTube 广告

**用途**：解除 YouTube 贴片广告的阻挡，让原本的播放或抓取任务继续。
**读者**：已经读过《AI 代理使用计算机》与《远程桌面控制》，能起 daemon、能列举窗口、能注入输入的执行者。本文只补一件事——在这件小事上，哪些做法看着合理、实际必然失败。
**适用范围**：Linux X11 上实测通过。其他平台见第 5 节。第 2 节第 2 条的完整演算见附录 A。

## 1. 分工：读走浏览器接口，写走原生输入

这是全部结论里最重要的一条。跳过按钮不接受合成点击，所以必须把「读」与「写」拆给两条不同的通道。

| 环节 | 用什么 | 为什么不能只靠另一条 |
|---|---|---|
| 判断有无广告、剩多少秒、按钮在哪 | 浏览器自身的调试协议，执行页面内脚本 | 无障碍树里网页内容残缺；在树里按名字找「跳过」会命中 `Skip navigation` 这类同名陷阱 |
| 真正按下按钮 | 驱动的原生输入，且必须声明前台模式 | 默认模式命中元素后会改走无障碍语义动作，对播放器完全无效，却依然返回成功 |

判断输入是否为真货的唯一凭据是返回值里的通道字段：`global_input` 是真实输入，`accessibility` 是空炮。

## 2. 七个必然踩到的坑

1. **点击要显式声明前台模式**。不写就退化成无障碍语义动作，结果看上去成功、页面毫无变化。这是最容易白白浪费一轮的地方。
2. **坐标要换算，而且不能只算一个**。页面脚本给的是视口坐标，驱动收的是屏幕上的设备像素，两者之间隔着缩放比与窗口装饰偏移。实测偏差可以小到十五个视口像素——对着视频画面那种几百像素的大靶子看不出来，对着 85×36 的按钮就是次次打空。做法是先算出基点，再在垂直方向上下各试一处，用「广告是否立刻结束」当判据。演算过程见附录 A。
3. **不要用页面脚本模拟点击**。该按钮要求真实用户手势，`element.click()` 对它无效。调试协议里那条受信任输入的路在 Linux 上被驱动主动禁用，原因是它会激活窗口、抢走使用者的焦点。
4. **按钮的矩形可能是空的**。部分广告返回的矩形是四个零，此时只能退回像素路线：截图、定位、再换算坐标。像素路线只能给出估算值，同样要用网格搜索兜住。
5. **成功判定要写严，否则会把「广告自己播完」记成成功**。两个条件必须同时成立：点击前剩余秒数大于四秒，且点击后广告立即结束。只看广告标识消失是最常见的误判。
6. **广告不是每次都有**。必须循环切换视频，直到出现可跳过的广告。一轮没出现属正常现象，不是失败。
7. **不要动使用者自己开着的浏览器**。它通常拒绝被附着，理由是窗口无法归属到某个无障碍顶层，要解决就得重启它并加上调试参数，不值得为省事去动。用独立的配置目录另起一个实例。

另有两处环境层面的细节：驱动自带的截图工具可能因权限审查而不可用，截图需改走系统自身的 X11 手段；自行启动的浏览器实例，收尾时要连同它的临时配置目录一并删除。

## 3. 最小流程

1. 在图形会话内起 daemon，用临时单元，用完即停。
2. 用独立配置目录起一个浏览器实例，开调试端口，并强制开启无障碍渲染。
3. 循环打开视频，用页面脚本问三件事：是否正在播放广告、跳过按钮的矩形、广告剩余秒数。
4. 按钮存在且剩余超过四秒时，换算坐标、以前台模式点击、立刻重问一次。
5. 收尾：停 daemon、停浏览器、删配置目录与中间脚本。

## 4. 怎么证明真的成功了

| 证据 | 要看的内容 |
|---|---|
| 页面脚本 | 广告标识为假、播放未暂停、正片播放进度在推进 |
| 屏幕像素 | 点击前画面里有那个跳过按钮，点击后按钮消失、正片画面出现 |
| 运行日志 | 剩余秒数从两位数直接跳到正片总时长 |

三者互相独立，缺一条就只能算「可能成功」。尤其注意点击与验证之间不要插入等待，否则无法区分是自己点的还是它自己播完的。

## 5. 未验证的平台

macOS 与 Windows 未经实测，已知需要重新确认的点有二。其一是输入注入的权限模型不同，前台模式与调试协议的受信任输入在两个平台上未必被同样禁用；其二是窗口装饰偏移的数值不同，坐标换算必须重新标定。

# 附录 A：一次完整的坐标演算

以下数字全部来自实测，不是示例假值。

## A.1 换算模型

页面脚本给出的坐标以 CSS 像素计，原点在被测量元素的视口左上角，不含任何浏览器界面。驱动接受的坐标以设备像素计，原点在屏幕左上角，已经包含窗口在屏幕上的位置、窗口边框与浏览器自身的界面高度。只要窗口几何不变，两者之间就是一个缩放加一个平移：

$$p_{\text{dev}} = s \cdot p_{\text{css}} + b$$

| 变量 | 含义 | 本例实测值 |
|---|---|---|
| $s$ | 一个 CSS 像素折合多少设备像素 | $2$ |
| $b$ | 平移量，单位设备像素 | $(44,\ 262)$，为脚本当时实际所用 |
| $\delta$ | 垂直分量的偏差，单位设备像素 | $30$，由 A.4 反推 |

$s=2$ 的来源：窗口外框量得 $3200 \times 2000$ 设备像素，而页面视口量得 $1600 \times 1000$ CSS 像素，两者相除即得。窗口尺寸与视口尺寸都要实测，不要假定缩放比为 1。

## A.2 从按钮矩形到落点

页面脚本报出按钮矩形 $R=(x_0,y_0,w,h)=(982,\ 566,\ 85,\ 36)$，四项均为 CSS 像素。取其中心：

$$c = \left(x_0 + \frac{w}{2},\ y_0 + \frac{h}{2}\right) = \left(982 + 42.5,\ 566 + 18\right) = (1024.5,\ 584)$$

代入模型：

$$x = s \cdot c_x + b_x = 2 \times 1024.5 + 44 = 2093$$
$$y = s \cdot c_y + b_y = 2 \times 584 + 262 = 1430$$

落点是 $(2093,\ 1430)$。点击后广告仍在播放。

## A.3 为什么差三十个设备像素就打不中

按钮换算到设备像素后是 $170 \times 72$：

$$w_{\text{dev}} = s \cdot w = 2 \times 85 = 170,\qquad h_{\text{dev}} = s \cdot h = 2 \times 36 = 72$$

而垂直方向的平移量事后证明大了 $30$ 设备像素，即十五个 CSS 像素。这个数字占按钮高度的 $42\%$：

$$\frac{30}{72} \approx 0.42$$

误差会随 $s$ 线性放大，所以同一份「差一点」的偏移，在高分辨率屏幕上会以两倍的设备像素数落到画面上。另外这个量级只与按钮自身尺寸作比较才有意义：同一个偏移打在视口里 $170 \times 72$ 的按钮上是废的，打在那块 $1600 \times 900$ 的播放器画面上则毫无感觉——这正是它难以被察觉的原因。

## A.4 网格搜索与步长怎么定

设估算基点为 $\hat p$，按钮在某一个轴向上的设备像素高度为 $h_{\text{dev}}$，以步长 $t$ 取三个采样点 $\hat p - t$、$\hat p$、$\hat p + t$。每个采样点本身能覆盖以它为中心、宽为 $h_{\text{dev}}$ 的一段区间，三点并起来没有空隙的条件是

$$t \le h_{\text{dev}}$$

于是估算误差 $e$ 的可容忍范围是

$$|e| \le t + \frac{h_{\text{dev}}}{2}$$

本例 $t = 30$、$h_{\text{dev}} = 72$，容差为 $30 + 36 = 66$ 设备像素，折合 $33$ 个 CSS 像素。三次实测：

| 采样点 | 点击后广告剩余 | 判定 |
|---|---|---|
| $(2997,\ 1598)$ | $25 \to 24$ 秒 | 无效 |
| $(2997,\ 1628)$ | $24 \to 23$ 秒 | 无效 |
| $(2997,\ 1568)$ | $\to 204$ 秒，即正片总时长 | 命中 |

命中点在基点上方 $30$ 设备像素处，与 A.3 里那个偏差同量级。这说明垂直方向几十个设备像素的误差属于常态，无论它来自换算偏移还是来自图像估算，所以网格搜索是必需的，不是保险起见。

## A.5 结论：不要去把 $b$ 标定准，直接搜

$b$ 会随窗口在屏幕上的位置、窗口边框、浏览器界面高度与页面缩放而变化。逐个标定既费事又脆弱——窗口一挪，标定就作废。网格搜索把问题从「算准一个仿射常数」换成「试三个点、用严格判据挑出真命中的那个」，并且容差可以由 $t$ 与按钮尺寸显式计算出来。

按钮更小或尺寸未知时取 $t = h_{\text{dev}}/2$ 并五采样，只要始终满足 $t \le h_{\text{dev}}$ 就不会留空隙。搜索方向可缓存：同一个窗口里，命中点相对基点的偏移是稳定的，找到一次之后后续广告直接偏移到位，一两次试错即可，不必每次都扫三个点。
